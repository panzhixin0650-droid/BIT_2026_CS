# 服务端管理员 UI 全局设计标准

本文档规定 `server/` 服务端及同进程管理员端的界面设计原则。它只约束视觉层级、信息组织和交互体验，不规定 Qt 控件、文件结构、具体尺寸或代码实现方式。

## 1. 设计目标

- 让管理员快速完成当前任务，而不是阅读产品宣传内容；
- 让状态、操作和结果一眼可识别；
- 保持界面克制、专业、稳定，避免装饰干扰业务判断；
- 在视觉美观的同时，保证键盘操作、错误修正和不同显示环境下的可用性；
- 统一登录页、数据概览、列表、详情、弹窗和反馈信息的行为与视觉语言。

## 2. 核心原则

### 2.1 业务优先

每个页面首先回答三个问题：当前在哪里、当前状态是什么、下一步能做什么。标题、数据、状态和主要操作应形成清晰的优先级，次要内容不能抢占主要任务的注意力。

### 2.2 少即是多

页面只展示完成当前任务所必需的信息。装饰性标语、重复解释、宣传语、课程演示信息和不会影响当前决策的背景说明不应出现在主要操作区域。

### 2.3 说明与界面逻辑分离

“使用说明”不等于“UI 设计”。操作界面中的文字应服务于识别、输入、决策和反馈；较长的背景介绍、产品功能清单、课程 Demo 账号、运行环境说明和概念解释应放在使用文档、开发文档或帮助入口中，而不是通过大量小字堆在页面上。

特别是登录页：不放功能宣传列表、登录说明、Demo 账号、数据源/运行模式说明或其他非必要辅助文案。登录页只保留品牌识别、必要字段、主要操作和必要的错误反馈。

### 2.4 一致性

相同含义使用相同的名称、颜色、位置和交互方式。成功、警告、错误、禁用、空数据和加载状态应在所有页面保持一致，不因页面不同而改变含义。

### 2.5 面向运营用户，而不是面向开发过程

管理员 UI 的使用者是负责站点、设备、用户、订单和营收管理的运营人员。界面应围绕他们的工作任务、业务判断和操作结果设计，不应把开发阶段的内部逻辑直接设计成用户功能或视觉元素。

Repository、SQLite、TCP、Mock、内存模式、调试开关、代码分层、数据库表结构、内部状态机和测试数据等属于实现细节，原则上不出现在面向运营人员的普通界面中。只有当某个技术信息直接影响运营决策，并且经过明确的产品需求确认时，才可以用用户能理解的业务语言呈现。

## 3. 信息层级

- 页面标题：说明当前模块或任务；
- 区块标题：组织相关内容，帮助扫描；
- 核心数据：突出数量、金额、状态和时间等决策信息；
- 主要操作：每个页面保持明确的首要操作；
- 次要操作：降低视觉权重，避免与主要操作竞争；
- 辅助信息：只有在理解或完成当前任务确实需要时才展示；
- 说明性内容：默认移出主界面，放入使用说明或帮助内容。

页面不应同时拥有多个同等强度的视觉焦点。对于列表和仪表盘，应先让用户看到整体状态，再提供筛选、查看和修改操作。

## 4. 文字规范

- 使用短句、明确的动词和用户熟悉的业务词汇；
- 标签说明控件的用途，不用含糊或仅靠上下文猜测；
- 不使用大段小字号文字弥补不清晰的信息架构；
- 不把错误原因、使用教程和产品宣传混写在同一段文字中；
- 重要提示应靠位置、标题、图标或结构表达，不只依赖颜色；
- 占位文本只能作为示例，不能替代永久可见的字段标签；
- 操作按钮的文字应描述动作，例如“登录”“保存”“删除”，避免使用含义不明确的“确定”“处理”等词；
- 术语、单位、时间格式和状态名称遵循服务端协议及业务文档，不在不同页面自行改名。

## 5. 登录页规范

登录页是单任务页面，目标是让管理员迅速、安全地完成登录。

应保留：

- 简洁的品牌识别；
- 清晰的“管理员登录”标题；
- 账号和密码的可见标签；
- 账号输入、密码输入和登录操作；
- 登录失败或服务不可用时的明确反馈。

不应保留：

- 功能宣传语或业务模块清单；
- “登录后台，查看……”之类的解释性小字；
- 课程 Demo 账号、测试提示或默认凭证展示；
- SQLite、内存、数据源或运行模式提示；
- 与登录任务无关的链接、插图、统计数字和状态卡片。

登录表单应保持视觉集中，输入顺序自然，主要按钮突出但不过度装饰。登录失败时保留用户输入，提示应帮助修正问题，同时避免泄露账号是否存在等敏感信息。

## 6. 表单与操作规范

- 每个输入项都有清晰、稳定的标签；
- 输入状态至少能区分默认、聚焦、填写、错误、禁用和提交中；
- 用户提交后应看到明确的处理中状态，避免重复提交；
- 主要操作使用一个稳定的主视觉样式，同一页面不设置多个互相竞争的主按钮；
- 破坏性操作应降低误触概率，并在必要时要求确认；
- 不设置没有明确价值的“清空表单”或“重置全部”操作；
- 错误提示应靠近相关字段或操作位置，说明问题和修正方向；
- 错误出现时不清除用户已经填写的内容。

## 7. 数据概览、列表与详情

- 仪表盘突出趋势、总量、异常和需要处理的事项，不用装饰填满空白；
- 卡片只承载一个清晰指标或一组紧密相关指标；
- 表格优先保证列名、单位、状态和时间可读，避免为了显示更多列而牺牲扫描效率；
- 列表筛选与搜索应靠近列表，结果区域保持稳定，避免操作后页面跳动；
- 详情页按“基本信息—实时状态—可执行操作”的顺序组织；
- 空数据、加载失败和无权限不能显示成空白页面，应提供清楚的状态反馈；
- 不把数据库字段原样堆给管理员，展示内容应围绕管理任务组织。

### 7.1 列表排版与列宽

列表是高频工作区，优先保证扫描速度和操作可达性，不追求“每个字段都放在一行”。

- 不默认把最后一列拉伸填满剩余空间。最后一列通常是“操作”，应保持紧凑、固定在右侧；剩余空间分配给名称、地址等主要内容列。
- 列宽按内容重要性分配：身份/名称列较宽，状态和数量列中等，ID、类型、单位和操作列较窄。长文本使用省略号，悬停或详情视图查看全文，不强行撑宽整张表。
- 操作列只放一个可见的“详情”或一个主操作，其余低频/危险操作收进“更多”菜单；不让多个大按钮把表格推得很宽。
- 表头和单元格保持单行优先；只有地址、错误原因等确实需要阅读的内容允许换行。避免每行高度因某一列长文本而剧烈变化。
- 表格使用轻量分隔线和适度留白，不使用厚重边框、强阴影或大面积色块。悬停、选中和展开状态应有细微但清晰的背景变化。
- 数字、金额、数量和状态保持稳定对齐：数字右对齐或按列统一对齐，文本左对齐，状态使用短标签；单位紧跟数值且格式统一。
- 站点主表不铺经纬度、创建时间等低频字段；这些字段放详情。可见列数量以一个窗口内无需横向滚动为目标，确需更多字段时使用详情而不是继续压缩字号。

### 7.2 轻量化密度

- 默认正文和表格文字使用舒适的常规字重，不通过加粗和放大制造“重要感”。粗体只用于页面标题、关键数值和必要的状态强调。
- 推荐层级：页面标题 22–24 px，区块标题 16–18 px，正文/表格 14–15 px，辅助标签 12–13 px；辅助文字不低于 12 px，且不能承载关键操作或关键数据。
- 行高约为字号的 1.4–1.6 倍，表格行保持紧凑但可点击；按钮和输入框避免过高的上下内边距，减少“卡片堆叠”的笨重感。
- 卡片只在需要分组或强调指标时使用。普通列表不再为每一行套卡片；页面通过留白、标题和细线分组。
- 圆角、阴影、描边和强调色应节制使用：同一层级只保留一种主要容器表达，避免“圆角套圆角”。

### 7.3 字体和文字层级

- 中文优先使用系统无衬线字体；保证数字、英文和中文基线协调，不混用过多字体。
- 页面标题使用清晰而不过重的字重（建议 600–700）；正文、表头和标签使用 400–600。整页不应出现大面积 700/800 粗体。
- 颜色、字号和位置共同表达层级；不能用浅灰小字承载管理员必须阅读的信息。
- 标签、按钮和状态名称使用短而具体的业务词。表头避免冗余词，例如“站点名称”可简化为“站点”，但不能牺牲含义。
- 占位文本是示例，不替代可见标签；不在搜索框下方堆放解释段落。

### 7.4 配色和状态

- 采用中性浅背景、白色内容面和单一品牌强调色，形成“内容优先”的轻界面。品牌色只用于主按钮、当前导航、焦点和少量关键链接。
- 状态色语义固定：正常/可用使用绿色，进行中/待处理使用橙色，故障/危险使用红色，停用/不可用使用中性灰；同时显示文字或图标，不能只靠颜色。
- 正文与背景、表头文字与表头背景、按钮文字与按钮背景均保持足够对比度；关键正文目标达到 WCAG 2.2 AA 的 4.5:1，对大字号可采用 3:1 下限。
- 不为每种状态设置不同的强背景块。优先使用短标签、细边框或小图标，减少视觉噪声；危险操作颜色只出现在操作本身和确认反馈中。
- 聚焦、悬停、选中、禁用状态应有不同但克制的视觉反馈。禁用控件降低对比度但仍能辨认，不使用“看起来像可点击”的灰色文字。

### 7.5 操作区布局

- 页面工具栏采用“左侧搜索/筛选，右侧主操作”的稳定结构；主操作最多一个高强调按钮，其余使用次级按钮。
- 操作区与表格之间保留明确间距，不用大块说明文字填充空白。
- 行级操作固定在最右侧，详情是最容易发现的入口；删除、停用、开机、关机、重启等操作放入更多菜单并依据状态禁用。
- 复杂详情使用右侧抽屉或内容页，避免在列表中嵌套多个重型弹窗。关闭详情后恢复原列表位置、筛选和展开状态。

## 8. 状态、错误与反馈

- 成功、进行中、警告、错误和不可用状态应有一致的文字、结构和视觉表达；
- 不能只用红绿颜色表达状态，应同时使用文字、图标或位置差异；
- 错误信息应具体、简短、可行动，避免只显示“操作失败”；
- 反馈不应遮挡用户需要继续查看的内容；
- 不使用与实际结果不符的成功提示；
- 影响数据的操作完成后，应让用户能立即看到更新后的状态。

## 9. 视觉与可访问性

- 使用稳定的中性背景、清晰的内容层级和有限的强调色；
- 颜色用于表达状态和操作优先级，不作为唯一信息载体；
- 正文、标签、按钮和表格文字保持足够的字号、字重和对比度；
- 聚焦状态必须清晰可见；
- 交互元素的可点击区域应足够，不把重要操作做成难以点击的小文字链接；
- 支持键盘按合理顺序移动和提交，窗口缩放后主要内容仍可用；
- 文字、表格和图表应避免过度依赖颜色、细线或低对比度灰字。

## 10. 文档与界面的边界

以下内容原则上写入使用说明、开发文档或版本文档，不放入普通业务页面的说明性小字：

- 产品背景和功能宣传；
- 课程 Demo 账号和开发环境信息；
- 数据库、Repository、TCP 或 Mock 的实现细节；
- 开发阶段的内部流程、代码分层、调试开关和测试数据说明；
- 完整操作教程和概念解释；
- 版本变更、已知限制和开发注意事项。

界面只在用户当前任务需要时提供最短的上下文提示；其余内容通过文档承载。

运营人员看到的应是业务概念，例如“设备状态”“站点可用性”“订单异常”和“营收趋势”，而不是“Repository 模式”“SQLite 连接”“Mock 桩状态”或其他开发术语。技术实现可以支撑界面，但不应成为界面的组织逻辑。

## 11. 设计评审清单

提交管理员 UI 变更前，应确认：

- 页面是否有明确的首要任务和视觉焦点；
- 是否删除了不影响当前任务的说明性小字；
- 是否把开发阶段的内部逻辑误设计成了运营用户功能或界面元素；
- 登录页是否只保留必要的品牌、字段、操作和反馈；
- 字段是否有清晰标签，错误是否可理解和可修正；
- 主要操作、危险操作和次要操作是否有清楚的层级；
- 状态是否不依赖颜色单独表达；
- 空数据、失败、加载和提交中状态是否可识别；
- 窗口缩放和键盘操作是否仍然可用；
- 界面文字是否与服务端协议、单位和状态定义一致。

## 12. 参考规范

本标准主要参考以下公开资料，访问日期：2026-09-03：

- [Material Design 3 — Text fields](https://m3.material.io/components/text-fields/guidelines)：字段标签、输入状态和表单层级；
- [Material Design 3 — Buttons](https://m3.material.io/components/buttons/guidelines)：按钮层级、主要操作和交互状态；
- [W3C WAI — Labeling Controls](https://www.w3.org/WAI/tutorials/forms/labels/)：表单控件应有清晰标签，不能只依赖占位文本；
- [Nielsen Norman Group — Form Design](https://www.nngroup.com/articles/web-form-design/)：减少不必要字段、避免重置按钮、保留错误输入并提供明确反馈；
- [GOV.UK Design System — Error message](https://design-system.service.gov.uk/components/error-message/)：错误提示应具体、靠近字段、保留用户输入并支持修正。
- [Material Design 3 — Typography](https://m3.material.io/styles/typography/overview)：字阶、字重、行高和文字层级应服务于阅读和信息优先级；
- [Carbon Design System — Data table](https://carbondesignsystem.com/components/data-table/usage/)：表格应控制信息密度，支持展开行、行操作和适当的列布局；
- [Carbon Design System — Filtering](https://carbondesignsystem.com/patterns/filtering/)：筛选控件应靠近结果，并区分即时筛选与需要确认的复杂筛选；
- [W3C WCAG 2.2 — Contrast minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)：正文和控件文字应满足可读性对比度要求。
