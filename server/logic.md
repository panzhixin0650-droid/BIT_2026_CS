# 服务端业务逻辑与管理员端交互逻辑

> 状态：讨论稿，只记录设计，不授权实现
>
> 日期：2026-09-03
> 范围：`server/` 服务端和同进程 Qt 管理员端

## 1. 设计边界

当前以五张表和现有 `AdminFacade` 为事实基础：`users`、`admins`、`charging_stations`、`charging_piles`、`charging_orders`。Repository 是唯一 SQL 入口，ApplicationService 负责校验和状态变更，电桩仍由 `MockPile` 表示。

本文件只设计业务规则和 UI 交互，不新增 SQL、数据库迁移、TCP 接口或实现代码。UI 不出现 SQLite、Repository、TCP、Mock、数据库文件、开发模式等技术概念。

## 2. 先确定的交互结论

### 2.1 搜索与筛选分开

两者是两种不同操作，不共用一个“查询”按钮：

| 控件 | 作用 | 触发方式 | 规则 |
| --- | --- | --- | --- |
| 搜索框 | 关键词包含匹配 | 点击“搜索”或按回车 | 不因每次输入刷新；不改变筛选控件 |
| 下拉/复选筛选 | 状态、区域、站点等精确筛选 | 选择后立即生效 | 不需要再点搜索；不改关键词 |
| 日期范围 | 时间条件筛选 | 选完起止日期后点击“应用” | 起止日期校验后生效 |
| 重置 | 清空搜索和筛选 | 点击“重置” | 恢复完整列表 |

实现上，当前数据量较小，可先加载列表后在 UI/业务层分别应用关键词和筛选；数据量增大时再把独立参数加到服务端查询。即使底层一次请求同时带两个参数，用户感知仍必须是“搜索”和“筛选”两个独立动作。

搜索框不放解释性小字。若需要占位提示，只使用一行短词，如“搜索站点名称或地址”；不在控件下方增加说明段落。

### 2.2 列表、详情和按钮位置

采用“列表摘要 + 详情视图”的渐进式披露：列表只放管理员做判断所需的信息，完整字段和关联记录放到详情页/抽屉。详情必须重复列表已显示的字段，再补充其余字段，避免管理员失去上下文。

- **主操作**（新增站点、新增电桩、导出等）放在列表工具栏右上角，位置固定、每页最多一个主要蓝色按钮。
- **批量或页面级操作**（筛选、重置、刷新）放在工具栏左侧或搜索区；不与主操作混成一排难以区分的按钮。
- **单行操作**放在表格最右侧“操作”列。保留一个常用的“详情”按钮；删除、停用、开关机、重启等危险或低频操作放入“更多”菜单，并根据状态禁用不可用项。
- **详情入口**不只依赖整行点击。整行可选中，点击明确的“详情”按钮进入详情；双击整行可作为桌面端快捷方式，但不是唯一入口。这样既可发现、可键盘操作，也不会把选中行和打开详情混为一件事。
- 详情使用右侧抽屉或独立内容页，不用多层小弹窗承载复杂信息；关闭后返回原列表、保留搜索、筛选、排序和展开状态。

### 2.3 站点与电桩的主从关系

站点是主实体，电桩是从实体。站点列表每行提供第一列的展开箭头；展开后在该行下方显示该站点的电桩摘要，不跳转、不复制站点字段。展开内容至少有：桩编号、快/慢充、额定功率、状态、累计次数、累计时长和可执行设备操作。

“详情”按钮打开站点详情，详情页上半部是完整站点资料，下半部是同一站点的电桩列表；电桩行也可打开电桩详情。站点列表和电桩管理列表可以分别存在，但站点页面必须能看见所属电桩，这是运营判断站点可用性的主路径。

## 3. 站点业务规则

### 3.1 新建

必填：站点名称、区域、详细地址、经度、纬度、统一电价（分/kWh）。可选：初始电桩数量，默认 0，范围 0–100。

- `stationId`、创建时间和初始状态由服务端生成，禁止表单填写。
- 数量为 0：只建空站点，之后从电桩管理新增桩。
- 数量大于 0：站点和完全相同数量的默认桩一次事务提交；失败全部回滚。当前 Demo 可自动生成唯一桩编号，快慢充交替，默认功率分别为 60 kW/7 kW。
- 成功后使用服务端返回的真实 ID 和完整站点详情刷新列表，并自动展开新站点。若当前搜索/筛选使新站点不可见，提示“已创建，但当前条件下不可见”，提供“清除条件”。
- 区域已有 `charging_stations.region` 字段，不新增区域表。当前不强制站点名称唯一，是否允许同名留待后续确认。

### 3.2 列表主信息

站点主表优先显示：站点名称、区域、地址、桩数（总数/可用数）、在线率、当前电价、运营状态、操作。站点 ID 可显示在次要位置；经纬度和创建时间放详情，避免主表过宽。

### 3.3 删除

- 服务端先检查该站点是否存在任何订单（包括已取消和历史完成订单）。
- 有订单：拒绝物理删除，建议停用站点；保留站点、桩和订单历史。
- 无订单：同一事务内删除站点及其全部电桩；成功后刷新列表和展开行。
- 确认框必须写清站点名称、影响的桩数量以及“有订单不能删除”，不使用含糊的“确定吗”。

## 4. 电桩业务规则

### 4.1 新建

必填：所属充电站、桩编号、类型（快充/慢充）、额定功率。所属站点必须从有效下拉项选择，不能置空；站点不存在或已停用时拒绝。`pileId` 由数据库生成，状态默认为 `IDLE`，累计次数和时长从订单聚合、初始为 0。桩编号必须唯一，重复时明确报错，不能静默覆盖。

创建成功后刷新电桩列表、所属站点的桩计数和已展开内容。站点总数、可用数、在线率均由电桩实时聚合，不在站点表中手工维护。

### 4.2 删除

- 无订单且处于 `IDLE`/`OFFLINE`：允许二次确认后删除。
- 有任何订单：禁止物理删除，改为 `OFFLINE` 或停用站点，以保留订单关联。
- `RESERVED`/`CHARGING`：禁止删除，必须先完成订单流程。
- 删除站点和删除电桩都由 ApplicationService 调 Repository，Qt UI 不直接写 SQL。

### 4.3 状态和设备操作

当前单一状态字段的管理语义如下：

| 操作 | 可操作状态 | 成功状态 | 说明 |
| --- | --- | --- | --- |
| 开机/上线 | `OFFLINE` | `IDLE` | 恢复可用，不创建订单 |
| 关机/下线 | `IDLE` | `OFFLINE` | 进行中订单不能关机 |
| 重启 | `IDLE`、`OFFLINE` | `IDLE` | 调用 Mock；不改变订单 |
| 标记故障 | `IDLE`、`OFFLINE` | `FAULT` | 为后续报修准备 |
| 故障恢复 | 本期无普通操作 | 保持 `FAULT` | 由后续检修/报修流程解除 |

`RESERVED`/`CHARGING` 禁止关机、重启和删除；`FAULT` 不能被普通重启清除。统计映射保持：在用=`RESERVED + CHARGING`，闲置=`IDLE`，故障/不可用=`FAULT + OFFLINE`。

电桩列表主信息：桩编号、所属站点、类型、功率、状态、累计充电次数、累计时长、操作。点击“详情”补充桩 ID、完整状态和关联站点资料；不伪造当前表没有的厂商、心跳、安装时间或报修字段。

## 5. 用户管理

### 5.1 列表和交互

主表显示管理员最常用的信息：手机号、昵称、余额、状态、注册时间、操作。用户 ID 放次要位置；当前订单数若未由服务端聚合，先不在列表伪造。

- 搜索：手机号或昵称包含匹配，点击搜索/回车生效。
- 筛选：正常/已冻结；选择后立即筛选。
- 行操作：右侧“详情”和“更多”；冻结/解冻属于状态操作，放更多菜单并在执行前检查进行中订单。

### 5.2 详情

详情重复列表字段，并补充用户 ID、订单统计、累计消费和最近订单。当前只有 `listUsers`、`listOrders`，第一版可在已加载数据中按 `userId` 聚合；数据量增大再增加只读详情/过滤接口。存在 `RESERVED`、`CHARGING` 或 `PENDING_PAYMENT` 订单时不允许冻结，冻结不删除余额和历史订单。

## 6. 订单管理

### 6.1 列表主信息

主表用于快速判断“谁、在哪个站点/桩、发生了什么、金额多少”：订单号、用户（当前可先显示用户 ID，手机号/昵称需映射）、站点、桩编号、模式、状态、时长、电量、金额、创建时间。内部 ID 和所有时间戳不全部铺在主表。

### 6.2 查询、筛选、详情

- 搜索：订单号、用户手机号或桩编号关键词，点击搜索/回车生效。
- 筛选：订单状态、站点、模式、日期范围；选择离散条件立即生效，日期范围点击应用。
- 默认创建时间倒序；当前 Demo 可本地过滤，数据量增大后再分页和服务端过滤。
- 右侧保留“详情”入口。详情重复列表字段，再展示订单 ID、用户/站点/桩 ID、预约/开始/结束/支付时间、价格快照、最终金额等完整 DTO 字段。
- 订单详情只读，不提供改金额、改状态、改电量、删除订单等破坏事实的按钮。

## 7. 统一页面行为

- 每个列表都有加载中、空结果、加载失败、正常结果；空结果使用“没有匹配记录”等业务语言。
- 新增、删除、状态变更遵循“提交中 → 成功/失败 → 刷新受影响区域”。
- 成功后尽量保留原搜索、筛选、排序和展开状态；因筛选不可见时明确提示原因。
- 危险操作必须二次确认；不可用操作显示禁用状态并说明原因，不能让管理员点击后才得到模糊错误。
- 状态颜色、文字和操作权限一致：绿色表示可用/正常，橙色表示进行中，红色表示故障/冻结/失败；颜色不能是唯一信息。
- 详情关闭后回到原列表位置；键盘可聚焦搜索、筛选、详情和操作按钮。

## 8. 当前接口/数据库下的实施分层

### P0：先修正现有闭环，不改表

1. 站点创建成功展示真实 ID、刷新并处理当前搜索/筛选；明确 0 桩和批量默认桩两条路径。
2. 把站点列表的搜索与区域筛选做成独立交互；删除搜索框周围说明性小字。
3. 站点行展开所属电桩，站点/电桩/用户/订单增加只读详情入口；优先复用已加载 DTO。
4. 修正站点删除提示和有订单保护，保持安全级联规则。

### P1：扩展服务端内部边界，仍可不改表

1. `createPile`、`deletePile` 及站点存在性、编号唯一性校验；
2. `powerOn`、`powerOff`、`restart`、`markFault` 状态转换；
3. 站点详情和电桩详情的只读聚合；
4. 用户/订单本地聚合无法满足数据量后，再增加服务端过滤参数。

### P2：需要单独确认并更新契约/迁移

分页和联表用户信息、站点启停操作、报修工单/故障恢复、设备命令日志、管理员账号/RBAC/密码管理。不能因为 UI 想展示就直接新增表或网络接口。

## 9. 调研依据

访问日期：2026-09-03。

- [Material Design 3 — Search](https://m3.material.io/components/search)：搜索用于查找内容，输入与结果反馈应保持清晰，不用额外说明堆叠界面。
- [Material Design 3 — Date pickers](https://m3.material.io/components/date-pickers/overview)：日期范围使用明确的起止输入和可验证反馈。
- [Carbon Design System — Data table](https://carbondesignsystem.com/components/data-table/usage/)：表格提供展开行、行级菜单和受控信息密度；主操作与行操作分层。
- [Ant Design — Table](https://ant.design/components/table/)：展开行适合展示主记录的关联明细，避免离开列表上下文。
- [Nielsen Norman Group — Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)：先显示完成任务所需的信息，细节按需披露。
- [GOV.UK Service Manual — Design](https://www.gov.uk/service-manual/design)：围绕用户任务组织页面，使用直接语言，并为加载、空、错、成功状态提供反馈。

这些资料是交互原则参考，不改变当前课程 Demo 的五表数据库、Mock 边界和模块所有权。
