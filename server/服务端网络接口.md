# 服务端网络接口

本文档记录服务端代码中**已经完成、客户端现在可以对接**的 TCP 接口。它是联调速查表，不替代正式协议契约；字段语义发生冲突时，以 [`../contracts/overall-interface-v1.md`](../contracts/overall-interface-v1.md) 为准，以服务端 `RequestRouter` 的实际接入状态判断接口能否调用。

当前接口版本：V1

最后更新：2026-09-03

当前实现：默认使用 SQLite Demo 数据库，token 仍保存在内存

## 1. 连接信息

| 项目 | 当前值 |
| --- | --- |
| 传输协议 | TCP 长连接 |
| 默认地址 | `127.0.0.1` |
| 默认端口 | `45678` |
| 字符编码 | UTF-8 |
| 应用数据 | JSON object |
| 处理顺序 | 服务端按收到帧的顺序串行处理 |
| 服务端主动推送 | 当前没有 |

启动服务端：

```bash
cd /path/to/BIT_2026_CS
./build/server/server-app --database build/database/demo.db
```

服务端不自动创建表或播种；数据库初始化见 [`../database/README.md`](../database/README.md)。开发时可以使用 `--port <端口>` 更换监听端口，或显式传入 `--in-memory` 使用非持久化测试替身。当前服务端只绑定本机回环地址，客户端和服务端应先在同一台电脑联调。
SQLite 嵌入在同一个 `server-app` 进程中，由 Repository 直接读写本地数据库文件；它没有独立 IP、端口或 TCP 连接。

## 2. TCP 分帧

每条消息必须按以下格式发送，不能只把 JSON 文本直接写入 socket：

```text
+--------------------------+------------------------------+
| 4 字节无符号大端整数 N   | N 字节 UTF-8 JSON 消息体     |
+--------------------------+------------------------------+
```

- 长度字段表示 JSON 消息体的字节数，不包含前面的 4 字节；
- 消息体长度范围为 `1..262144` 字节；
- JSON 根节点必须是 object；
- 服务端支持半包、粘包和一次读取多帧；
- 非法长度、非法 JSON、非 object 根节点或非法信封会导致服务端断开该连接，不返回业务错误响应；
- 客户端应持续缓存收到的数据，读取完整的 4 字节长度和完整消息体后再解析。

客户端与服务端都可以直接复用 [`../shared/protocol/`](../shared/protocol/) 中的 `encodeFrame`、`FrameDecoder`、请求/响应信封和 DTO。

## 3. JSON 信封

### 3.1 请求

```json
{
  "version": 1,
  "type": "station.list",
  "requestId": "client-1001",
  "token": "登录返回的 token",
  "data": {
    "region": "浑南区"
  }
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | :---: | --- |
| `version` | integer | 是 | 当前固定为 `1` |
| `type` | string | 是 | 接口消息名，不能为空 |
| `requestId` | string | 是 | 客户端生成，不能为空，用于匹配响应 |
| `token` | string | 条件 | 除登录和 ping 外，当前已实现接口均需要 |
| `data` | object | 是 | 无参数时也必须发送 `{}` |

### 3.2 响应

```json
{
  "version": 1,
  "type": "station.list",
  "requestId": "client-1001",
  "code": 0,
  "message": "OK",
  "data": {
    "items": []
  }
}
```

- 响应会原样回显请求的 `version`、`type` 和 `requestId`；
- 只有 `code == 0` 才表示成功；
- `data` 始终为 object，失败时通常为 `{}`；
- 客户端按 `code` 处理业务分支，`message` 用于日志或默认提示。

## 4. 当前已完成接口

| type | 需要 token | 请求 `data` | 成功响应 `data` |
| --- | :---: | --- | --- |
| `system.ping` | 否 | `{echo?: string}` | `{echo?: string, serverTime: datetime}` |
| `auth.user.login` | 否 | `{phone: string}` | `{token, isNewUser, user: UserDto}` |
| `auth.logout` | 是 | `{}` | `{success: true}` |
| `user.profile.get` | 是 | `{}` | `{user: UserDto}` |
| `user.profile.update` | 是 | `{nickname: string}` | `{user: UserDto}` |
| `wallet.recharge` | 是 | `{amountCents: integer}` | `{balanceCents: integer}` |
| `station.list` | 是 | `{longitude?, latitude?, region?, keyword?}` | `{items: StationDto[]}` |
| `station.detail` | 是 | `{stationId: integer}` | `{station: StationDto, piles: PileDto[]}` |

### 4.1 `system.ping`

用于确认 TCP、分帧、JSON 信封和服务端路由全部正常。

请求：

```json
{
  "version": 1,
  "type": "system.ping",
  "requestId": "ping-1",
  "data": {"echo": "hello"}
}
```

成功响应的 `serverTime` 是 UTC ISO 8601 时间；传入 `echo` 时服务端原样返回。`echo` 如果存在必须是 string。

完整示例：[请求](../contracts/examples/system-ping.request.json) / [响应](../contracts/examples/system-ping.response.json)

### 4.2 `auth.user.login`

请求 `data`：

```json
{"phone": "13800000001"}
```

- 手机号必须是 11 位数字；
- 已存在的正常用户直接登录；
- 不存在的手机号会在当前 Repository 中创建用户，默认昵称为 `用户` 加手机号后 4 位；默认 SQLite 模式下会持久化到服务器本地数据库；
- 冻结用户返回 `40301 FORBIDDEN`；
- 成功后客户端保存返回的 `token`，并在后续请求的信封顶层携带它。

成功响应 `data`：

```json
{
  "token": "服务端生成的 token",
  "isNewUser": false,
  "user": {
    "userId": 1,
    "phone": "13800000001",
    "nickname": "演示用户0001",
    "balanceCents": 20000,
    "status": "ACTIVE",
    "createdAt": "2026-06-04T11:53:41Z"
  }
}
```

完整示例：[请求](../contracts/examples/auth-user-login.request.json) / [响应](../contracts/examples/auth-user-login.response.json)

### 4.3 `auth.logout`

请求 `data` 为 `{}`。成功后服务端删除该 token，客户端也应清除本地 token。token 缺失、为空或无效时返回 `40101 INVALID_SESSION`。

### 4.4 `user.profile.get`

请求 `data` 为 `{}`，成功返回 `{user: UserDto}`。适合客户端进入个人中心或充值完成后刷新当前资料与余额。

### 4.5 `user.profile.update`

请求 `data`：

```json
{"nickname": "新的昵称"}
```

昵称长度必须为 1 到 32 个字符。当前只支持修改昵称；头像由客户端保存在本地，不通过 TCP 上传。

### 4.6 `wallet.recharge`

请求 `data`：

```json
{"amountCents": 500}
```

充值金额必须是 `1..1000000` 的整数，单位为分。成功返回充值后的余额：

```json
{"balanceCents": 20500}
```

当前是课程 Demo 模拟充值，没有第三方支付流程。客户端不要使用浮点元金额请求服务端，例如 5 元应发送 `500`。

### 4.7 `station.list`

请求字段：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | :---: | --- |
| `longitude` | number | 否 | 经度，范围 `-180..180`；必须与 `latitude` 同时出现 |
| `latitude` | number | 否 | 纬度，范围 `-90..90`；必须与 `longitude` 同时出现 |
| `region` | string | 否 | 区域精确筛选，例如 `浑南区` |
| `keyword` | string | 否 | 在站名和地址中进行不区分大小写的包含查询 |

- 只返回状态为 `ACTIVE` 的站点；
- 有坐标时计算本次请求的 `distanceKm` 并按距离升序返回；
- 没有坐标时 `distanceKm` 为 `null`，按 `stationId` 升序返回；
- 预测可用时返回 `predictedCongestion`，并选择一个低拥堵站点标记 `recommended=true`；
- 用户坐标只用于本次计算，不保存。

完整示例：[请求](../contracts/examples/station-list.request.json) / [响应](../contracts/examples/station-list.response.json)

### 4.8 `station.detail`

请求 `data`：

```json
{"stationId": 1}
```

`stationId` 必须是大于 0 的整数。成功返回站点信息和该站全部电桩；站点不存在或已停用时返回 `40401 NOT_FOUND`。

完整示例：[请求](../contracts/examples/station-detail.request.json) / [响应](../contracts/examples/station-detail.response.json)

## 5. 客户端需要解析的 DTO

### 5.1 `UserDto`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `userId` | integer | 用户 ID |
| `phone` | string | 手机号 |
| `nickname` | string | 昵称 |
| `balanceCents` | integer | 余额，单位分 |
| `status` | string | `ACTIVE` 或 `FROZEN` |
| `createdAt` | string | UTC ISO 8601 时间 |

### 5.2 `StationDto`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `stationId` | integer | 站点 ID |
| `name` / `region` / `address` | string | 站名、区域、地址 |
| `longitude` / `latitude` | number | 经纬度 |
| `priceCentsPerKwh` | integer | 单价，分/kWh |
| `status` | string | `ACTIVE` 或 `DISABLED` |
| `totalPileCount` | integer | 总桩数 |
| `availablePileCount` | integer | 当前空闲桩数 |
| `onlineRatePercent` | number | 在线率百分数，例如 `50.0` |
| `distanceKm` | number/null | 本次查询距离 |
| `predictedCongestion` | string/null | `LOW`、`MEDIUM` 或 `HIGH` |
| `recommended` | boolean | 是否为本次推荐站点 |

### 5.3 `PileDto`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `pileId` / `stationId` | integer | 电桩 ID、所属站点 ID |
| `pileCode` | string | 电桩展示编号/扫码内容 |
| `pileType` | string | `FAST` 或 `SLOW` |
| `ratedPowerKw` | number | 额定功率，kW |
| `status` | string | `IDLE`、`RESERVED`、`CHARGING`、`FAULT` 或 `OFFLINE` |
| `chargeCount` | integer | 已停止充电次数 |
| `totalChargeSeconds` | integer | 累计充电时长，秒 |

## 6. 错误码

| code | message | 客户端建议处理 |
| ---: | --- | --- |
| `0` | `OK` | 读取 `data` |
| `40001` | `INVALID_REQUEST` | 检查字段是否缺失、类型或范围是否错误 |
| `40101` | `INVALID_SESSION` | 清除 token，返回登录页并重新登录 |
| `40301` | `FORBIDDEN` | 当前已用于提示用户被冻结 |
| `40401` | `NOT_FOUND` | 刷新页面并提示目标不存在或不可用 |
| `50001` | `INTERNAL_ERROR` | 显示通用服务端错误 |
| `50301` | `SERVICE_UNAVAILABLE` | 客户端在连接失败、断线或超时时使用 |

`40102`、`40901..40903` 和 `42201` 已在 V1 契约中保留，但不是当前 8 个已完成用户 TCP 接口的主要成功链路错误。客户端仍建议统一保留这些错误码枚举，供后续订单接口使用。

## 7. 尚未开放的 TCP 接口

以下消息名已在 V1 契约和共享常量中定义，但截至 v1.0 尚未接入服务端 `RequestRouter`：

| 状态 | type |
| --- | --- |
| 待实现 | `prediction.latest` |
| 待实现 | `order.current` |
| 待实现 | `order.reserve` |
| 待实现 | `order.cancel` |
| 待实现 | `order.start` |
| 待实现 | `order.progress` |
| 待实现 | `order.stop` |
| 待实现 | `order.pay` |
| 待实现 | `order.list` |

当前调用这些消息会返回 `40001 INVALID_REQUEST`，客户端暂时不要把它们作为可用功能。它们实现后，应先更新本文档的“当前已完成接口”和 [`版本日志.md`](版本日志.md)，再通知客户端联调。

管理员界面不使用 TCP。它和服务端运行在同一个 `server-app` 进程内，通过 `AdminFacade` 调用 `ApplicationService`。

当前管理员端进程内能力还包括：自定义日期 Dashboard、创建/删除电桩、电桩上线/下线/标记故障/重启，以及站点、电桩、用户和订单详情。新增站点时可提交逐桩的 `pileCode`、`pileType` 和 `ratedPowerKw` 明细，站点与初始电桩原子创建；它们没有新增客户端 TCP 消息，不属于客户端网络对接范围。

## 8. 客户端对接顺序

建议按以下顺序联调：

1. 连接 `127.0.0.1:45678`；
2. 调用 `system.ping` 验证收发和分帧；
3. 使用 `13800000001` 调用 `auth.user.login` 并保存 token；
4. 调用 `user.profile.get`；
5. 调用 `station.list`，再用返回的 `stationId` 调用 `station.detail`；
6. 调用 `wallet.recharge`，再读取资料确认余额；
7. 调用 `user.profile.update`；
8. 调用 `auth.logout` 并清除客户端 token。

演示用户：

| 手机号 | 用途 |
| --- | --- |
| `13800000001` | 正常登录和联调 |
| `13800000004` | 冻结用户，验证 `40301` |
| `13800000005` | 待支付用户，为后续订单联调保留 |

当前 token 仍保存在服务端内存中，用户、余额、站点和桩状态保存到 SQLite。服务端重启后业务数据保留，但客户端必须重新登录；为简化联调，连接断开后也建议重新连接并重新登录。普通请求等待超过约 5 秒时，客户端可以提示服务不可用，但不要自动重试充值等写操作。
